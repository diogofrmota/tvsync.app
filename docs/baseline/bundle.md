# Bundle baseline

Measured against `pre-refactor-baseline` (commit `babdcf4`) using a real
production build, not estimates.

## Methodology note (read before trusting the numbers below)

`@next/bundle-analyzer` (added in this commit) **does not work with Turbopack
builds** — `next build` defaults to Turbopack in Next 16 and the analyzer
prints "not compatible with Turbopack builds, no report will be generated."
The documented workaround is `next build --webpack`, but in this sandbox that
OOM-killed the Node process at both the default heap limit and at
`--max-old-space-size=12288` (12 GB) — the interactive treemap report could
not be generated here. The `pnpm analyze` script (added in this commit) runs
`ANALYZE=true next build --webpack` and should produce the interactive report
normally, given more memory headroom than this sandbox had (try
`NODE_OPTIONS=--max-old-space-size=16384 pnpm analyze` or larger first if it
still OOMs).

What follows instead is a **direct measurement of the real build artifacts**:
every route's `page_client-reference-manifest.js` (Next writes one per route)
was parsed to get the exact, deduplicated set of chunk files that route's
client tree references, then each chunk was measured on disk (raw) and gzip
level 9 (a reasonable proxy for wire size). This is more precise than an
analyzer's treemap for the specific "how much JS does this route ship"
question, though it doesn't visualize which modules make up a shared chunk
the way a treemap does.

## The finding: there is effectively no route-level code splitting

The spread across all 34 pages is **519.7 KB to 609.1 KB raw — an 89 KB
range**, and gzip compresses the two ends to 143.3 KB vs 173.2 KB — a 30 KB
difference between the *lightest possible page in the app* and *the single
heaviest*. `/privacy` and `/terms` are static server-rendered text with no
client interactivity at all, yet they still ship **143 KB of gzipped JS**.
That is not page-specific code — it's the fixed floor every route pays
regardless of what it actually does, and it dominates the total for every
single route measured. Route-level code splitting exists in principle (each
route does have its own manifest and its own chunk subset), but in practice
almost everything referenced is shared framework/UI-library weight, not
page-specific logic.

## What's in the floor

Chunk-content scanning (grepping for literal `chakra-` class-name strings,
which survive minification because they're runtime string values, not import
specifiers — Chakra/Emotion don't preserve package-name strings the way
source maps would):

- **22 of 244 total chunk files across the whole app reference Chakra UI
  class names**, totaling **750 KB raw** — at least 44% of the app's entire
  client-side JS footprint touches Chakra-styled UI somewhere in that chunk
  (this overstates pure-library weight, since a chunk mixing Chakra usage
  with page-specific code counts entirely; it understates in the sense that
  chunks without a literal `chakra-` string can still import Chakra's
  non-DOM-emitting internals).
- Root/shared chunks (loaded by literally every page, per
  `build-manifest.json`'s `rootMainFiles`) total **447 KB raw / 132.5 KB
  gzip** on their own, before any route-specific code.
- No source maps are generated by default
  (`productionBrowserSourceMaps` unset), so exact per-package attribution
  beyond the `chakra-` string signal would need a temporary source-mapped
  build — worth doing if the UI-library decision (Phase 4.2) needs a harder
  number than "at least 44%."
- No literal `react-icons` or `framer-motion` strings survive minification to
  scan for the same way; nothing found here rules out or confirms a
  tree-shaking problem with either. Framer-motion is only imported in 2 files
  and react-icons in 18, per the earlier codebase survey — worth a follow-up
  check with a source-mapped build rather than asserting either way from this
  data.

## Bottom line for Phase 4

This is a direct, measured answer to the UI-library question in
`PRE_REFACTOR.md`'s Phase 4.2: **every route in this app currently pays a
~143 KB gzip minimum before a single byte of that route's own content
renders**, and that floor is dominated by Chakra/Emotion (at minimum 44% of
total shipped JS references it directly). A zero-runtime alternative
(Tailwind, CSS Modules) would attack exactly this floor rather than any
individual route's code — which is also why the 89 KB raw spread between
routes is the wrong number to optimize first; the ~520 KB floor everything
sits on top of is the one that matters at the scale this app is targeting.
